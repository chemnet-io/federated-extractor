Task 3: QLever endpoint with different access levels
====================================================

Goal
----
Provide a QLever SPARQL endpoint for the RDF generated by this repository,
while ensuring that clients can only perform operations allowed by their
application role.

Task 3A - QLever foundation (current branch: task3-A)
-----------------------------------------------------
Owner: Task 3A developer

1. Add a Qleverfile for the federated-extractor RDF dataset.
2. Add a small, deterministic RDF fixture for local setup and testing.
3. Document how to build the index, start QLever, and run smoke queries.
4. Add an automated smoke-check client for the running endpoint.
5. Define the environment-variable contract without committing secrets.
6. Keep QLever's privileged access token private and supplied at runtime.

Task 3A does not implement API roles or expose privileged QLever operations
to clients.

Task 3B - Authorization gateway
-------------------------------
Owner: Hassan

1. Extend API-token storage so each token has a role.
2. Support at least reader, writer, and admin roles.
3. Add FastAPI endpoints that proxy allowed SPARQL operations to QLever.
4. Allow reader, writer, and admin roles to query the graph.
5. Allow only writer and admin roles to perform SPARQL updates.
6. Reserve QLever administrative operations for the admin role.
7. Add tests proving that forbidden operations are rejected.
8. Never return or expose the internal QLever access token to API clients.

Integration contract
--------------------
Task 3B should use these environment variables:

QLEVER_URL=http://localhost:7001
QLEVER_ACCESS_TOKEN=<set locally; never commit>

Suggested API permission model:

POST /sparql/query
  Allowed roles: reader, writer, admin

POST /sparql/update
  Allowed roles: writer, admin

Administrative operations
  Allowed role: admin

Security boundary
-----------------
Clients authenticate to FastAPI with their own application API tokens.
FastAPI checks the associated role and then communicates with QLever.
QLever should not be directly exposed to untrusted clients. Only FastAPI
uses QLEVER_ACCESS_TOKEN for privileged QLever operations.

Merge order
-----------
Task 3A should be merged first because it defines the QLever endpoint and
environment contract. Task 3B can then integrate against that stable
contract.
